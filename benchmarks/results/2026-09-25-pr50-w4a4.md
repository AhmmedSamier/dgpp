# W4A4 NVFP4 expert prefill: PR #50 follow-up

The submitted W4A4 path wrote BF16 down-projection rows, but the
host-orchestrated reference still read those rows as FP32. Both host
output APIs now share format-aware accumulation with device-segmented
prefill. This preserves the production BF16 intermediate and FP32 routed
sum, including transitions to and from the small-batch W4A16 fallback.

The memory plan now includes the lazy activation codes, block scales and
row globals for eligible NVFP4 layers. At Qwen's 2048-token chunk,
hidden width 2560 and top-10 routing, these total 29,573,120 bytes
(28.2 MiB) per rank. Qwen's calibrated default and GLM's forced dynamic
mode use the same eligibility calculation as dispatch. Shapes beyond the
quantizer's 16384-element width limit fall back to W4A16.

The follow-up also resolves CMake conflicts with current master while
retaining both kernels and test targets, releases each W4A4 benchmark
case's allocations, and gives that GPU test the suite's no-device skip
behavior. Diagnostic chain dumps materialize bypassed gather/activation buffers and
read down rows in their actual format, so checksums remain meaningful with
the fused W4A4 path.

Regression coverage:

- Host FP32 and BF16 output against device-segmented output at 137, 1,
  then 137 tokens, with calibrated NVFP4 experts and top-2 routing.
- Host-only Qwen memory plans under default, disabled and forced modes;
  threshold, TP-width, FP8, shared-row and quantizer-width exclusions.
- Activation scales on both TP ranks and after an NVFP4 resident-image
  restore that does not repopulate the host-side scale fields.

Validation on 2026-09-25:

- The CI preset (`DGPP_WERROR=ON`) built the server, host-test targets,
  `moe_w4a4_test`, `glm_moe_test`, `qwen_loader_test`, `qwen_forward_test`,
  `qwen_moe_test` and `qwen_tp_test`.
- All 27 host CTest cases excluding checkpoint-dependent cases passed,
  including the three new workspace-plan modes and server startup tests.
- `moe_w4a4_test` returns the expected CTest skip with no visible GPU.
- A CPU probe using the real dispatch code and mock CUDA launchers
  reproduced the original BF16/FP32 mismatch and confirms the corrected
  host path reads BF16. It does not validate GPU kernel execution.
- After the owner authorized a maintenance window, the four-rank deployment
  stopped cleanly, with identical operation streams across ranks. All four
  GPUs were confirmed idle before GPU/RDMA testing.
- The new host/device output regression fails against the original PR's
  `moe_layer.cpp` with an FP32 output mismatch and passes with the fix.
- All 11 selected CTest cases passed with no skips: `qwen_forward_fixture`,
  `qwen_forward_smoke`, `qwen_forward_smoke_yarn`, `qwen_forward_cross_limit`,
  `qwen_qsa_prefill`, `qwen_moe_test`, `qwen_loader_test`, `qwen_tp_test`,
  `moe_w4a4_test`, `glm_moe_test` and `moe_w4a4_layer_test`. The TP test
  exercises worlds 2 and 4 over loopback RDMA on one node; it is not a new
  multi-node W4A4 benchmark. The loader's activation-scale image-restore

- The new output regression also passed separately with unfused SwiGLU,
  FP32 down rows, W4A4 disabled, and diagnostic chain dumps. Diagnostic

- The W4A4 kernel test's worst normalized error against its FP64 dot oracle

- The original serving binary and settings were restored after testing.
  All four ranks were alive, and `/health` and `/v1/models` returned HTTP
  200 for the original model. The running binary's SHA-256 matched the
