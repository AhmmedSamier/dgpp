# C1 difference analysis (2026-09-15)

The default Qwen candidate's observed C1 difference is about **−0.25%**
across the five prompt classes: **0.016–0.164 fewer tokens/s**, or
**2–31 ms more per 320-token response**. This is a small measured shift.
The campaign's zero-median-slowdown gate flags it without establishing
whether the implementation caused it or whether it is operationally material.

This analysis uses the retained runs and server logs; it required no new
cluster run. [Derived data and source hashes](2026-09-15-c1-analysis.json)
and the [full campaign](2026-09-15-qwen-batching-prefill.md) retain the evidence.

## Default Qwen: absolute size

Qwen FP8 TP2, four configured slots, native MTP depth 1, prefill budget zero.
One request at a time, greedy, thinking disabled, 320 output tokens, five
repeats/class/build. Baseline session: 06:48–06:51 UTC; candidate:
06:55–06:58 UTC. Each class has one prefix miss followed by four hits,
with identical prompt/output lengths and cached-token counts across builds.

| Class | Baseline tok/s | Candidate tok/s | Difference tok/s | Difference | Extra time / 320 tokens |
|---|---:|---:|---:|---:|---:|
| Prose | 44.676 | 44.600 | −0.077 | −0.172% | +12.3 ms |
| Code | 48.594 | 48.438 | −0.155 | −0.319% | +21.1 ms |
| JSON | 50.151 | 50.135 | −0.016 | −0.032% | +2.1 ms |
| Math | 47.158 | 47.013 | −0.145 | −0.307% | +20.9 ms |
| Chat | 41.318 | 41.155 | −0.164 | −0.396% | +30.8 ms |

Rates are class medians including prefill and completion delivery. Extra
time is `320 / candidate_rate - 320 / baseline_rate`; it is not a kernel
latency measurement or an extrapolation to longer outputs.

The equal-class geometric mean of median rate ratios is **−0.245%**.
Pooling all 25 responses instead gives **45.974 → 45.876 tok/s (−0.213%)**,
and mean response time **6.96049 → 6.97538 seconds (+14.89 ms)**.
These summaries weight observations differently and are explicitly separate.

## Timing scope and cache sensitivity

| Measurement | Equal-class change | Interpretation |
|---|---:|---|
| Full request-wall rate, all five repeats | −0.245% | Includes prefill and final delivery |
| Historical first-to-last-visible-output rate | −0.256% | Still contains client/server buffering effects |
| Full wall rate, four prefix hits only | −0.241% | Supplementary check; first cold samples remain in the primary result |
| Server admission-to-retirement interval rate | −0.227% | Excludes prefill and final HTTP delivery; includes host/runtime work |

The server interval comes from millisecond log timestamps between the
first-token admission and retirement. Its median increase is 26 ms for
prose, 18 ms for code, 9 ms for JSON, 13 ms for math, and 12 ms for chat.
It is not a CUDA event timing. The similar small shift there means final
client delivery cannot explain the entire result.

Mean client response-time differences across all 25 requests decompose as:

| Component | Candidate minus baseline |
|---|---:|
| Time to first visible output | −4.24 ms |
| First-to-last-visible-output interval | +13.82 ms |
| Last visible output to response completion | +5.11 ms |
| Client phase overhead | +0.19 ms |
| **Total** | **+14.89 ms** |

These are differences of means, so the unrounded components add exactly.
They should not be added to differences of class medians above. The
HTTP loop has a 25 ms idle timeout; a single such interval is approximately
0.3–0.4% of these response durations. This provides scale for delivery
variation, not a hard timer resolution or proof that HTTP caused the shift.

## How repeatable was the reference?

The unchanged Qwen binary's later baseline was **0.44–1.24% slower by
class**, with an equal-class mean ratio of **−0.797%**, than its initial
baseline. The unchanged GLM binary's restored baseline was **0.48–1.04%
slower**, with an equal-class mean ratio of **−0.779%**. These comparisons
include session/cache preparation differences and dynamic clock state;
they demonstrate campaign reproducibility limits, not an independent
random-noise distribution that can be subtracted from candidate results.

Within a session, some results are much tighter. For example, the four
warm code responses span **48.590–48.611 tok/s** at baseline and
**48.438–48.468 tok/s** in the candidate, with no overlap. There is a
consistent shift in that pair of sessions. Five adjacent repeats from one
deployment per build do not identify its cause. Treating them as five
independent deployment A/B experiments would understate uncertainty; no
confidence interval for a causal implementation effect is claimed here.

## Work performed and other configurations

All 25 matched Qwen requests have identical visible transcripts, usage
counts, decode-pass counts and logged acceptance percentages. Passes per
320-token response are **181 / 166 / 160 / 170 / 195** for
prose/code/JSON/math/chat in both builds. No additional speculative passes
account for the difference. The executable CUDA fatbin sections are
byte-identical, and default C1 graph node/edge counts match. Host/runtime
cost and system state remain possible contributors.

GLM candidate versus the fresh restored baseline gives an equal-class wall
change of **+0.181%**, with classes from **−0.151% to +0.538%**; its
historical output-span summary is **+0.038%**. This provides no consistent
evidence of a material default-configuration GLM slowdown in this campaign.

Keep the optional settings separate:

- Four Qwen slots plus budget 256: **−0.420%** equal-class C1 wall summary
  against the fresh baseline, with classes **−0.18% to −0.58%**.
- Eight Qwen slots plus budget 256: **−1.269%** against the initial four-slot
  baseline, with classes **−0.72% to −3.15%**. This is a different capacity
  configuration and has a larger observed C1 tradeoff. Its reference is
  also from a different session; the result does not isolate capacity cost.

## Interpretation

Default C1 is approximately unchanged at the campaign's observed
between-session reproducibility, with a small negative Qwen shift in the
fresh A/B. A sub-0.5% implementation cost remains possible. The current
data support reporting the effect size and uncertainty; the zero-threshold
failure alone does not demonstrate a material regression.

For a stronger causal answer, use multiple interleaved baseline/candidate
deployments (ABBA), identical cache preparation, continuous per-rank
telemetry and separate engine/client timings. Longer fixed-output runs
can reduce the proportional effect of response-delivery delays. Keep all
existing results when adding these measurements.
