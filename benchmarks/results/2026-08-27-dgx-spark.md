verbs completion handling, NIC-DMA→GPU visibility, memory contention, and
cuBLASLt heuristic selection.

## Network ceiling

```bash

  -q 4 -t 128 --report_gbits -p PORT [PEER]
```

| run | duration | lane 0 | lane 1 | aggregate |
|---|---:|---:|---:|---:|
| isolated lane 0 | 5 s | 107.64 Gb/s | — | 107.64 Gb/s |
| isolated lane 1 | 5 s | — | 107.64 Gb/s | 107.64 Gb/s |
| concurrent | 8 s | 97.98 Gb/s | 98.05 Gb/s | **196.03 Gb/s** |

Conclusion: each interface exposes one PCIe x4-limited lane of the cabled
200 Gb/s QSFP port. Both must be used for near-line-rate aggregate traffic.

## NIC DMA → GPU visibility

```bash
micro_ibv_smoke serve PORT --once --dev DEVICE --gid-index 3
micro_ibv_smoke verify --peer PEER:PORT --iters 10000 \
  --dev DEVICE --gid-index 3
```

| receive lane | changing payloads | GPU hash mismatches | timeouts |
|---|---:|---:|---:|
| 0 | 10,000 | 0 | 0 |
| 1 | 10,000 | 0 | 0 |

The post-hardening 1,000-iteration-per-lane reruns in the preceding table also
passed with the final transport binary.

The GPU polled the NIC-written sequence directly while the CPU only arranged
the QP and checked the result. Payload and doorbell were separate ordered RC
SEND work requests. This validates payload-before-doorbell visibility on this
exact CUDA/kernel/firmware stack.

## Shared-memory pressure from real RDMA writers

Baseline `micro_zerocopy` run:

- `cudaHostAlloc` GPU read: 251.5 GB/s;
- `cudaMalloc` GPU read: 240.1 GB/s;
- flag round trip: 1.14 µs p50, 1.39 µs p99.

During two simultaneous incoming `ib_write_bw` streams, each sustaining 98.04
Gb/s:

- pinned GPU read: **218.4 GB/s** (13.2% below baseline);
- device GPU read: 208.6 GB/s;
- flag round trip: 1.12 µs p50, 1.42 µs p99.

Conclusion: zero-copy remains preferable to a 59.6 GB/s staging copy. Capacity
models that assume sustained dual-lane ingress provisionally derate
simultaneous GPU memory bandwidth by 15%; this stress-case value is not a
fixed inference penalty and must be revisited with the actual collective
schedule.

A final no-RDMA regression of the orderly-stop binary measured 252.5 GB/s
pinned read, 240.8 GB/s device-mapping read, 210.8 GB/s pinned write, and
1.12/1.41 µs flag p50/p99. CPU-writer proxies now touch only separate buffers;
the former same-buffer CPU/GPU data race was removed.

## cuBLASLt heuristic sweep

The final method first loads all SMs long enough to reach P0. Every valid
heuristic returned by cuBLASLt (up to 16 requested) is then measured in three
timed batches; candidate selection uses the median batch. Two independent
final process runs produced:

| shape | FP8 | BF16 |
|---|---:|---:|
| attention output, decode `1×4096×16384` | 231.8–238.3 µs | 578.3–581.4 µs |
| dense gate/up, decode `1×24576×4096` | 406.9–419.2 µs | 832.4–835.7 µs |
| lm head `1×154880×4096` | 2,798.0–2,844.3 µs | 5,364.7–5,528.2 µs |
| attention output, prefill m=2048 | 195.7–200.9 TFLOP/s | 93.4–94.9 TFLOP/s |
| dense gate/up, prefill m=2048 | 220.8–220.9 TFLOP/s | 95.6–95.8 TFLOP/s |

These supersede both the first-heuristic-only table and provisional runs that
began while the GPU was ramping from P8. Small decode shapes can be L2-warm and
must not be interpreted as DRAM peak.

## Local flow-control observation

For both active Ethernet interfaces:

- global pause RX/TX: on;
- DCB PFC priorities 0–7: off;
- `rx_out_of_buffer`: 0 at inspection time;
- cumulative priority-0 discards were nonzero, but they were not interval
  deltas and cannot be attributed to this run.

Switch configuration was not accessible from the node and is intentionally
not inferred from host state. The tests reached the physical-link ceiling
without a congestion symptom. Switch inspection and interval counter deltas
are optional diagnostics if a future four-node run shows drops, retries,
unstable throughput, or latency spikes.
