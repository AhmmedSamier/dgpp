# M5 deliverable 1 — epoch-based roster/startup and rank health over TCP (2026-08-29)

Implementation: `src/net/` (`tcp.{hpp,cpp}`, `roster.{hpp,cpp}`), deployment
driver `roster_check` (coordinator/rank/selftest), unit tests in
`tests/unit/net_test.cpp` (10 cases, loopback, in-process).

## Protocol (v1)

20-byte little-endian frame header (`magic 'DGPP' | version 1 | type |
reserved | epoch | payload_len`), types ANNOUNCE / ROSTER / HEARTBEAT /
HEARTBEAT_ACK / SHUTDOWN / REJECT. Rejection is a frame with a reason
string, never a bare close — a config error must be legible in the rank's
log. Control-plane only; never on the CUDA critical path (DESIGN §6).

Semantics validated:

- **Seal**: all-or-nothing startup — the coordinator waits for all
  configured ranks (or fails with exact progress, e.g. "1 of 2") and seals
  the roster at epoch 1. The coordinator's own rank 0 is an implicit member
  (`local_rank`).
- **Epochs**: monotonic, owned by the coordinator; every ROSTER frame
  carries the producing epoch. Rejoin after seal is refused in v1
  ("roster already sealed") — a replacement member would need a state
  consistency story first.
- **Eviction** has two triggers, both validated: process death (TCP EOF —
  SIGKILL on a real node) and unresponsiveness (heartbeat deadline,
  post-seal only). Evicted ranks receive their final roster so they can
  distinguish "evicted" from "coordinator lost".
- **Coordinator loss** is detected by the ranks' ack deadline and is fatal
  for the batch (DESIGN §5) — no coordinator failover in v1.

## Four-node validation (fabric subnet, 192.0.2.x)

Nodes: `node-a` (.11, coordinator/rank 0), `node-b` (.12, rank 1),
`node-c` (.13, rank 2), `node-d` (.14, rank 3). Binary built
once on the coordinator node and copied to each peer (identical aarch64
Linux); no per-node build.

Run 1 — happy path. `roster_check coordinator --world 4 --port 29500
--duration-ms 15000` locally, `roster_check rank --id {1,2,3} --host
192.0.2.11 --port 29500 --duration-ms 25000` via ssh on the peers:

- sealed epoch 1 with 4 members (implicit rank 0 included);
- all four processes agreed on the identical roster;
- coordinator's 15 s graceful shutdown reached every rank (all `stopped`),
  all exit codes 0.

Run 2 — injected rank death. Same layout; rank 3 SIGKILLed ~6.5 s in:

- coordinator detected the closed connection in ~30 ms, evicted rank 3,
  epoch 1 → 2 (3 members);
- both survivors logged the epoch-2 roster 30–40 ms after the kill;
- coordinator final roster 3/4 members, exit 1 by design (an evicted rank
  is a finding, not a success); survivors exited 0 via the graceful
  shutdown.

## Flakes found and fixed during hardening (loopback, before the node runs)

Each was a real protocol bug caught by stress (40+ consecutive runs), not a
sleep-race papered over with bigger budgets:

1. **join() returned the latest, not the first, sealed roster** — a rank
   evicted before its caller woke read an eviction roster "that did not
   contain it". The sealed roster is now frozen at receipt.
2. **The client ack deadline fired pre-first-roster** — pre-seal silence is
   normal (the coordinator is waiting for the remaining announces); the
   deadline is now a post-join liveness check only.
3. **The server's 500 ms announce deadline silently closed slow announces**
   under load — now 5 s; a dropped announce must never look like a dead
   coordinator.
4. **Heartbeat deadlines were enforced pre-seal**, silently closing
   healthy-but-slow ranks — deadlines protect sealed batches; pre-seal,
   the startup gate governs.
5. **join() both launched the worker and blocked for the first roster** —
   sequentially starting ranks in one thread deadlocked; the lifecycle is
   split into `start()` and `join()`.
6. The four-node run itself caught that `roster_check rank` never called
   `start()` (the loopback selftest did, so only real multi-process use
   exposed it).
