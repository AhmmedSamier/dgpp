## Protocol (as built; DESIGN §6/§6.1/§6.2)

Per (peer, lane) the bus owns TWO RC QPs — one per slot pool — so every
receive queue stays type-predictable: latency (8 KiB × 32) and bulk
(256 KiB × 16) traffic can never consume each other's differently-sized
receive buffers. Both pools share one pinned, remotely-writable slab per
(peer, lane), registered as one MR. Per-message traffic is the validated
flag-protocol shape: payload SEND (unsignaled) then doorbell SEND (signaled,
64-byte `StartSlot{seq, len}`); the doorbell receive CQE means the whole
message landed (RC ordering).

The credit grant is an unsignaled 64-byte RDMA WRITE of `BusCredit{hash,
slot, seq}` into the sender's registered completion cells — no CQE, no
consumed receive WR; the sender's engine polls the cell as a pinned flag,
the same visibility contract as the GPU acks. Slot recycling follows §6.4:
repost both receive WRs, then the credit WRITE, only after the doorbell CQE
*and* the consumer's ack are known.

Ring discipline (the non-obvious part): plain SENDs are consumed FIFO by
the peer's receive ring, so "slot" is a ring position, not a free buffer.
The sender assigns slots round-robin per (lane, pool) and may not skip a
busy position; the receiver recycles in ring order; credits return in ring
order. Break any leg of that and the doorbells claim the wrong buffers —
silently at first, loudly at the first sequence check.

The receive consumer is a persistent watchdog-bounded kernel per (peer,
lane), one block × 256 threads: all threads scan doorbell cells, one
message is claimed by shared-memory CAS, the payload is folded
cooperatively (golden-ratio pair mix, host-mirrored), and thread 0
publishes the ack with a system-scope release. The engine's real
per-collective consumers (§6.2, deliverable 3) replace it by launching with
`launch_consumers=false`.

## Validation

Loopback (in-process pair, real QPs through the fabric switch), 3× clean:

- latency ping 64 msgs: integrity via fold-hash per stripe, p50 ≈ 16–19 µs;
- credit recycling: 96 messages through a 4-slot ring;
- bulk 64 MiB: ≥ 4 stripes, **both lanes must contribute** (asserted on
  sender credits and receiver doorbells), xor-hash verified;
- latency-under-bulk: 256 latency messages while 24 × 16 MiB streams —
  all verified, p99 held under the CI budget;
- watchdogs: no receiver consumer → the request fails loudly in ≤ 600 ms
  (per-request or lane watchdog, whichever fires first); a consumer with a
  300 ms deadline exits on inactivity in 0.30 s;
- config mismatch (slot geometry) → rejected over TCP with a legible
  reason before any QP transition;
- stop while in flight → the waiter resolves, never hangs.

Two-node on the fabric (node-a ↔ node-b, both f0 lanes):

**Four-node mesh validation** (all four nodes, world=4, after the GID fix
below): every rank exchanges with every peer — 12 directed pairs, each
8/8 latency + 2/2 bulk (4 MiB), zero failures, orderly stops. The
endpoint-table distribution (rank 0 broadcasts everyone's per-peer lane
endpoints) and 12-QP bring-up are validated on real nodes; deliverable 3's
collectives start on known-good plumbing. Also reproduced in-process: the
bus_test `mesh_three_way` scenario runs a world=3 loopback mesh, 6 directed
pairs, in CI.

**The mesh found platform bug #8 — link-local GID selection.** Each port's
GID table sorts a `fe80::` RoCEv2 entry (index 1) ahead of the routable
IPv4-mapped one (index 3); the GID picker (inherited from the M0 tools)
took the first v2 entry. Link-local forwarding through the switch is
pair-dependent: some directed pairs worked, and everything into one node
was silently dropped — the same QP pair ran perfectly one way and RNR'd
forever the other. Fix: prefer the first non-link-local v2 GID (validated
across the mesh; loopback bulk also rose ~2.6→9.9 GB/s). The M0 per-lane
measurements were taken on link-local GIDs and remain valid for those
pairs, but the routable GIDs are now the deployment selection.

| run | result |
|---|---|
| latency 200 × 8 KiB | 200/200 verified, min 15.6 µs, p50 16.7 µs, p99 33.6 µs (full post→credit round trip incl. GPU fold + hash check) |
| bulk sequential 16 × 4 MiB | 16/16 verified, 256 stripes split 128/128 across lanes, 22.75 Gbps — correctness run; sequential messages drain the rings every message, so this is a floor, not the transport rate |
| bulk flood, window 16, 128 × 4 MiB | 128/128 verified, 164.89 Gbps |
| **bulk flood, window 32, 256 × 4 MiB (1 GiB)** | **256/256 verified, 178.45 Gbps = 91% of the measured 196.03 Gb/s wire ceiling**, stripes 2042/2041 across lanes |
| bulk flood, window 64, 512 × 4 MiB | 512/512 verified but 91.78 Gbps — deeper windows serialize in the engine's per-iteration budget; open tuning item |
| contention (400 latency + 64 MiB bulk) | 400/400 verified at p50 18.6 µs, p99 2.4 ms while both lanes striped |

The flood mode (`bus_check ping --window N`) keeps N requests in flight and
defers hash verification out of the timed section — every message is still
verified, but the per-message host costs stop polluting the throughput
number. Per-message latency under the window-32 flood (p50 5.66 ms) matches
the pipeline arithmetic (32 × 4 MiB ÷ ~22.6 GB/s), so the pipeline is
behaving as designed.

The flood also found a real protocol bug the correctness runs could not:
**the verbs contract retires an unsignaled WR's send-queue entry only at the
next signaled completion on that QP.** A QP that posts only unsignaled
credit writes — the receiver's bulk pool — fills its SQ monotonically and
dies at exactly `qp_depth` (observed: both lanes at 1024 credits posted).
Sequential and window-16 runs never crossed ~1024 recycles per lane, so the
bomb sat under every earlier validation; sustained prefill would have hit it
within ~256 MiB per lane-pair, and the one-hour soak would eventually have
found what the flood found in one run. Fix: signal every 16th credit
generation — bounded SQ occupancy plus real error visibility for the credit
path, at a small fraction of the CQ load.

Remaining gap to line rate (18 Gb/s, ~9%) and the window-64 regression are
measured open items for deliverable 3's tuning pass: engine memcpy per
stripe is in the timed path, the harness consumer processes one stripe at a
time, and ring recycling is strictly in-order. The M0 196 Gb/s ceiling was
measured with a raw SEND flood — no doorbells, acks, credits, or folding —
so some of that gap is the price of the correctness machinery.

## Bugs found and fixed during bring-up (all real, all in the record)

1. **Credit WRITE targeted our own endpoint** (rkey/slab_base of the local
   lane instead of the peer's) — the peer's HCA rejected the rkey, both
   QP ends flushed, the surviving lane wedged until its watchdog. The
   exchange table now stores the peer's lane endpoint at bring-up.
2. **Free-buffer slot choice broke ring alignment.** Plain SENDs are
   consumed FIFO by receive WRs, so the receiver cannot choose which slot
   a message lands in; picking "first free" send buffer desynchronized
   sender bookkeeping from receiver ring positions (doorbell seq 2 into a
   slot expecting 1). Fix: round-robin cursors, in-order recycle, credits
   in ring order.
3. **One QP per (peer, lane) mixed pool sizes on one receive queue.**
   With latency and bulk WRs interleaving on the same RQ, a 256 KiB bulk
   message could land in an 8 KiB latency receive buffer. Fix: one QP per
   pool (2 per peer-lane; 12 per node at TP=4).
4. **Persistent-kernel stream starvation.** Both lane consumers launched
   on one stream: kernel 0 never exits, so the lane-1 consumer never
   started — every scenario touching lane 1 froze. Fix: one stream per
   consumer. (§6.2's per-collective kernels avoid this class entirely.)
5. **`cudaFreeHost`'s implicit device synchronization.** In-process
   teardown of bus A waited out bus B's live persistent consumers (an
   idle-poll loop that never ends). Fix: two-phase stop —
   `quiesce()` stops engines and consumers and frees nothing; `stop()`
   tears down. Loopback pairs quiesce both sides before either stops;
   one-bus-per-process deployments never notice.
6. A watchdog-failed request could be reaped by `wait()` while a receive
   slot still referenced it — send slots now hold owning
   `shared_ptr`s until the credit clears.
7. **Unsignaled credit WRITEs never retire send-queue entries** (verbs
   contract: only a later signaled completion frees them). The receiver's
   bulk QP died at exactly `qp_depth` posts once the flood sustained >1024
   recycles per lane. Fix: signal every 16th credit generation.
8. **Link-local GID selection** (above): the first RoCEv2 GID per port is
   `fe80::`, and switch forwarding of link-local is pair-dependent —
   one-way silent drops. Fix: prefer the routable IPv4-mapped v2 GID.
   Found by the four-node mesh; invisible to any two-node test on the
   healthy pairs.
