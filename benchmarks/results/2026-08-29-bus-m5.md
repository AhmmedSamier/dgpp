## Protocol (as built; DESIGN §6/§6.1/§6.2)

Per (peer, lane) the bus owns TWO RC QPs — one per slot pool — so every
receive queue stays type-predictable: latency (8 KiB × 32) and bulk
(256 KiB × 16) traffic can never consume each other's differently-sized
receive buffers. Both pools share one pinned, remotely-writable slab per
(peer, lane), registered as one MR. Per-message traffic is the validated
flag-protocol shape: payload SEND (unsignaled) then doorbell SEND (signaled,
64-byte `StartSlot{seq, len}`); the doorbell receive CQE means the whole
message landed (RC ordering).

The credit grant is an unsignaled 64-byte RDMA WRITE of `BusCredit{hash,
slot, seq}` into the sender's registered completion cells — no CQE, no
consumed receive WR; the sender's engine polls the cell as a pinned flag,
the same visibility contract as the GPU acks. Slot recycling follows §6.4:
repost both receive WRs, then the credit WRITE, only after the doorbell CQE
*and* the consumer's ack are known.

Ring discipline (the non-obvious part): plain SENDs are consumed FIFO by
the peer's receive ring, so "slot" is a ring position, not a free buffer.
The sender assigns slots round-robin per (lane, pool) and may not skip a
busy position; the receiver recycles in ring order; credits return in ring
order. Break any leg of that and the doorbells claim the wrong buffers —
silently at first, loudly at the first sequence check.

The receive consumer is a persistent watchdog-bounded kernel per (peer,
lane), one block × 256 threads: all threads scan doorbell cells, one
message is claimed by shared-memory CAS, the payload is folded
cooperatively (golden-ratio pair mix, host-mirrored), and thread 0
publishes the ack with a system-scope release. The engine's real
per-collective consumers (§6.2, deliverable 3) replace it by launching with
`launch_consumers=false`.

The flood mode (`bus_check ping --window N`) keeps N requests in flight and
defers hash verification out of the timed section — every message is still
verified, but the per-message host costs stop polluting the throughput
number. Per-message latency under the window-32 flood (p50 5.66 ms) matches
the pipeline arithmetic (32 × 4 MiB ÷ ~22.6 GB/s), so the pipeline is
behaving as designed.

The flood also found a real protocol bug the correctness runs could not:
**the verbs contract retires an unsignaled WR's send-queue entry only at the
next signaled completion on that QP.** A QP that posts only unsignaled
credit writes — the receiver's bulk pool — fills its SQ monotonically and
dies at exactly `qp_depth` (observed: both lanes at 1024 credits posted).
Sequential and window-16 runs never crossed ~1024 recycles per lane, so the
bomb sat under every earlier validation; sustained prefill would have hit it
within ~256 MiB per lane-pair, and the one-hour soak would eventually have
found what the flood found in one run. Fix: signal every 16th credit
generation — bounded SQ occupancy plus real error visibility for the credit
path, at a small fraction of the CQ load.

Remaining gap to line rate (18 Gb/s, ~9%) and the window-64 regression are
measured open items for deliverable 3's tuning pass: engine memcpy per
stripe is in the timed path, the harness consumer processes one stripe at a
time, and ring recycling is strictly in-order. The M0 196 Gb/s ceiling was
measured with a raw SEND flood — no doorbells, acks, credits, or folding —
so some of that gap is the price of the correctness machinery.

## Bugs found and fixed during bring-up (all real, all in the record)

1. **Credit WRITE targeted our own endpoint** (rkey/slab_base of the local
   lane instead of the peer's) — the peer's HCA rejected the rkey, both
   QP ends flushed, the surviving lane wedged until its watchdog. The
   exchange table now stores the peer's lane endpoint at bring-up.
2. **Free-buffer slot choice broke ring alignment.** Plain SENDs are
   consumed FIFO by receive WRs, so the receiver cannot choose which slot
   a message lands in; picking "first free" send buffer desynchronized
   sender bookkeeping from receiver ring positions (doorbell seq 2 into a
   slot expecting 1). Fix: round-robin cursors, in-order recycle, credits
   in ring order.
3. **One QP per (peer, lane) mixed pool sizes on one receive queue.**
   With latency and bulk WRs interleaving on the same RQ, a 256 KiB bulk
   message could land in an 8 KiB latency receive buffer. Fix: one QP per
   pool (2 per peer-lane; 12 per node at TP=4).
4. **Persistent-kernel stream starvation.** Both lane consumers launched
   on one stream: kernel 0 never exits, so the lane-1 consumer never
   started — every scenario touching lane 1 froze. Fix: one stream per
   consumer. (§6.2's per-collective kernels avoid this class entirely.)
5. **`cudaFreeHost`'s implicit device synchronization.** In-process
   teardown of bus A waited out bus B's live persistent consumers (an
   idle-poll loop that never ends). Fix: two-phase stop —
   `quiesce()` stops engines and consumers and frees nothing; `stop()`
   tears down. Loopback pairs quiesce both sides before either stops;
   one-bus-per-process deployments never notice.
6. A watchdog-failed request could be reaped by `wait()` while a receive
   slot still referenced it — send slots now hold owning
   `shared_ptr`s until the credit clears.
7. **Unsignaled credit WRITEs never retire send-queue entries** (verbs
   contract: only a later signaled completion frees them). The receiver's
   bulk QP died at exactly `qp_depth` posts once the flood sustained >1024
   recycles per lane. Fix: signal every 16th credit generation.
8. **Link-local GID selection** (above): the first RoCEv2 GID per port is
   `fe80::`, and switch forwarding of link-local is pair-dependent —
   one-way silent drops. Fix: prefer the routable IPv4-mapped v2 GID.
   Found by the four-node mesh; invisible to any two-node test on the
   healthy pairs.

## Deliverable 3 — one-shot all-to-all all-reduce (in progress)

Design (DESIGN §6.3): every rank posts its full vector to every peer in one
dependency-free wave; one per-collective kernel stages the outbound slots
(GPU→engine handoff via a pinned control cell), waits the peers' doorbells,
folds with fp32 accumulation in canonical global-rank order (all ranks'
destinations bitwise identical — replicated compute stays in lockstep),
publishes standard acks, and stamps done. Credits stay off the critical
path: completion is the kernel's stamp, not the credit round trip.
Recursive doubling was recorded and rejected for this class (round j's
payload is round j−1's reduced output — a data dependency that serializes
the GPU→host→post→wire chain per round); reduce-scatter/allgather remains
the choice for the bulk/prefill class.

Correctness matrix (bitwise vs the canonical-chain host oracle):

| world | where | verify |
|---|---|---|
| 2, 4 | loopback, in CI (bus_test scenario_allreduce) | 8 collectives/rank, per-iteration bitwise, plus contract pins (consumers-running rejection, mode-closed sends, single-outstanding) |
| 2 | this node ↔ node-b | 30/30 final-iteration bitwise (earlier builds: 200/200 + 20/20 full-verify) |
| 4 | full mesh, all four nodes | 30/30 bitwise on every rank |

Latency (submit→wait, final engine policy):

| run | result |
|---|---|
| allreduce TP=2 | min 26.6 µs, p50 37.6 µs, p99 65-70 µs |
| allreduce TP=4 (full mesh) | min 36.7 µs, p50 ~44 µs, p99 ~143 µs, all four ranks in lock-step |

Kernel-internal spans at 2.42 GHz (ctl stamps): stage ~6 µs, doorbell
claim ~6 µs (message already arrived), fold+ack+reduce ~10 µs. The launch
(~10-30 µs, stream sync round trip ~150 µs amortized out of the loop)
dominates the fixed cost; §6.2's graph capture is the designed amortizer
for the decode path (next: forward integration).

Postmortem — the 2.5 ms phantom (found and fixed): the first collective
measurements sat at ~2.5 ms p50. GPU-side spans showed the doorbell waits
alternating 5 µs / 2.8 ms in a two-rank lock-step, ping-ponging which rank
ate the delay. Eliminated one by one: GPU idle/DVFS (a single multi-second
kernel kept the device busy the whole run — tail persisted; clock stamps
show 2.4 GHz in-kernel), module loading (CUDA_MODULE_LOADING=EAGER — no
change), engine poll cadence (pure hot spin — no change), write
visibility (kernel heartbeat — no change), cross-thread stream sync
(removed — no change). The tail was the engine's own idle policy
compounding with the waiter's wake: `std::this_thread::yield()` on the
"idle" path is a syscall that surrenders the timeslice (~2.2 ms of poll
latency per idle stretch, in a loop whose header says "never a syscall on
the hot path"), and bare condition-variable waits paid a CFS-timeslice
futex wake against the hot engine. The fixes — hot-spin window with no
syscall (2000 iterations, then a 50 µs sleep that is a power courtesy,
never a latency mechanism), spin-then-futex waits on a release-published
done flag (spin before taking the mutex; spinning under the mutex
deadlocks the completer — written, caught by measurement, fixed) — also
improved the harness path: latency_ping p50 16.5 → 12.1 µs,
latency-under-bulk 13.3 → 11.7 µs. Lesson recorded: idle-path policy is
latency policy; a "spin" branch that calls sched_yield is neither.

Gates on the final state: ci-local (WERROR) 21/21 (now 10 scenarios),
ASan 21/21, UBSan 21/21.

### Bugs found by the loopback (and fixed)

9. **Collective completion raced its own cleanup.** `complete_request`
   woke the waiter BEFORE the engine cleared the flight, so the woken
   model thread's next chunk submission raced the single-outstanding
   check and was rejected "one outstanding" — and the watchdog/fail_lane
   reap paths never cleared the flight at all, wedging the bus forever.
   Fix: every completion path clears the flight (and poisons) BEFORE
   completing the request; the watchdog clears a flight it reaps; a
   done-but-held flight is detected and cleared at the next pass.
10. **Allocation-phase device syncs vs spinning first collectives.**
    `cudaMallocManaged`/`cudaFree` and the loader's
    `cudaDeviceSynchronize` are whole-device barriers; a rank still
    constructing while a peer's first collective kernel spins on
    doorbells is a process-wide deadlock (the kernel waits for the
    constructing rank's post, the constructing rank's allocation waits
    for the spinning kernel). bus_check never allocated concurrently
    with collectives; the TP loopback was the first. Fix:
    `preconstruct_layers()` builds every layer object in the model ctor
    (no allocation ever happens in run_stack), and the runners barrier
    after construction — no rank's first collective can start while a
    peer still holds an allocation-phase sync. Post-startup the shape is
    safe (engines post from free threads; staggered per-layer loads and
    collectives coexist by construction).
11. **Stale-binary measurements** (again, third occurrence): ambiguous
    build output ("grep -c error" printed 0 on silent no-ops and a bare
    count on failures) plus failed-verify patches burned hours on runs
    of binaries that predated the fix under test. House rule now:
    verify the rebuild by content (`strings` for a new log line) or
    mtime before interpreting any run.

Engine hygiene from the bring-up: the collective kernel deadline is now
sized per deployment (the TP loopback uses 20 s — the 600 s consumer
default turns a wedged peer into a frozen process); the engine logs the
first-flight lifecycle (launch/ready/done) at INFO and dumps a stalled
flight's doorbell/ack state every 500 ms — the failure modes above were

TSan (one-off, not a house gate): the engine's submit/complete protocol
shows clean; the multi-model process surfaces the documented

### The staging seam: producing GEMMs write the collective source (d3)

`stage_next()` hands the model a pinned, device-writable buffer (a
dedicated self row in a new per-bus staging block, 8 generations deep);
the boundary GEMM writes the transport's fold source directly and
`allreduce_staged()` submits it. The kernel's snapshot pass (source ->
every peer's send row) stays — but it becomes a pinned fan-out, and the
device->slot copy disappears. The send-side insight: an RDMA SEND's local
address is any MR-registered memory, so only the doorbell's remote ring
position participates in ring discipline; the payload leaves from fixed
staging rows while the engine's cursor/credit machinery is untouched.

Three bugs the validation caught (all now recorded as design rules):

- **The alias race (the important one).** First cut: the handout WAS peer
  0's send row, and the kernel "skipped" its snapshot for pre-staged
  sources — so peer 0's post read a buffer the in-place fold was
  concurrently overwriting. The engine posts asynchronously when the
  ready bit lands; the fold starts after the claims — no ordering exists
  between them, so the post read pre-fold or post-fold bytes depending
  on timing. Loopback bus_test PASSED this twice (the post usually wins),
  then failed 4089/4096 elements on the third run — a silent-corruption
  class hiding behind a race we were winning. Fix: a dedicated self row —
  peer rows are send sources, the handout row folds in place, disjoint
  by construction. The kernel needs no pre-staged mode at all; it is the
  normal kernel with a pinned src that aliases dst (thread-per-element
  in-place fold is safe; the snapshots are taken before it).
- **The loopback device-sync hazard reintroduced by the test itself.**
  The staged bus_test rank worker used cudaDeviceSynchronize() after the
  producing kernel; at world 4 that is a whole-device barrier against
  three peer collective kernels spinning on this rank's doorbells — the
  §6.3 allocation-phase rule, exactly. 5 s of stall until the kernel
  deadline, then the watchdog cascade. Producing kernels run on a
  private stream and the worker STREAM-syncs; the model seam already had
  this right.
- **The harness barrier double-arrive.** rank_work's catch called
  arrive_and_wait() again when a forward-phase throw happened after the
  barrier had passed — `left` went negative, every rank futexed at the
  barrier forever, and the rank's error message was swallowed (the hang
  had no evidence in it). Rank workers now arrive exactly once and log
  the error loudly. The reducer's staged path also submitted through
  the normal allreduce() (rejected: handout held) — the visible symptom
  of that bug was entirely the swallowed hang.

Measured (two-node fabric, 6-layer mini fixture, T=8 x hidden 256 — one
collective per boundary, 12 collectives): md5-identical outputs across
ranks; TP-vs-oracle final hidden l2 0.0316 — the exact CI loopback value
(determinism across transports); collective p50 34.7 us on the clean rank
vs 38.3 us for the chunked device-path baseline (T=21) — the removed

### d3 bulk (RS+AG) bring-up — state at session end (WORKING TREE, not committed)

The bulk machine is implemented end to end (kernel, engine segment walk,
allreduce_bulk, reducer routing, tests) with four real bugs found and
fixed along the way, and ONE residual blocker narrowed to a fingerprint.
Not committed — the bus_test bulk scenario still fails on it.

Bugs found and fixed (all in the working tree):

- **The staging word-size mismatch.** The staging loop indexed u32
  pointers with a u64-word bound (`w*8 < bytes` with `d[w]=s[w]` copying
  4 bytes) — exactly half of every stripe staged. The engine and NIC
  faithfully shipped the half; the receiver's second half was zeros.
  The values-at-the-post instrument caught it (arena[2046]=0000 at post
  time). u64 words throughout now.
- **The __nv_bfloat16 truncation.** `uint16_t out = __float2bfloat16(x)`
  converts through __nv_bfloat16's float operator and TRUNCATES TO THE
  INTEGER — the fold wrote literal 1s (0x0001) for every element. The
  latency kernel never hit this (its dst is typed __nv_bfloat16*); any
  bf16 store through a uint16_t* must use __bfloat16_as_ushort.
- **The double-claim / early exit.** The claim scan's "already consumed"
  check on the pinned ack can read stale right after THIS kernel's own
  release-store published it (a visibility window on pinned flags);
  the same cell re-claims, arrived double-counts, the loop exits with a
  stripe's contribution missing (fingerprint: 16 claims, k=15 empty).
  The latency kernel survives the identical hazard ONLY through its
  per-peer s_got guard. Fix: claims are deduped in CTA-coherent shared
  (RS: per-(stripe,peer) bits; AG: per-(peer,stripe) bits) — correctness
  no longer hangs on pinned-flag visibility windows.
- **The segment-advance arena race.** A segment's done stamp does NOT
  imply its outbound posted (the posting loop can be credit-starved);
  advancing on done alone let the next segment's kernel overwrite arena
  rows the NIC had not read yet. The advance now waits for the global
  bulk TX retirement (doorbell CE seen == posted — exact, since harness
  bulk sends are closed under coll_mode).

Test-harness bugs (the loopback device-sync class bit THREE times this
session — now a recorded rule): cudaDeviceSynchronize in a rank worker
(staged scenario), then synchronous cudaMemcpy, then cudaMemset — all
device-wide barriers against peer spinning kernels. Every device op in
a loopback worker goes through a private stream. Plus the rank_work
catch arriving at the construction barrier twice (left goes negative,
every rank hangs with the error swallowed) — workers arrive exactly once
and log failures loudly.

The residual blocker, narrowed to a fingerprint on both loopback AND
two-node fabric (one rank per process — not a loopback artifact): the
bulk kernel's claim scan never sees mid-kernel NIC doorbell writes —
arrived=0/2 and arrived=0/4 with the arrivals visibly in the cells

claims fine). The LATENCY kernel sees its mid-kernel arrivals with the

in the bulk kernel's compiled claim loop specifically serves
launch-time state. Next session entry: with the double-claim noise now
removed from the experiment, diff the PTX/SASS of the two kernels' scan
loops from a clean slate (the latency scan compiles to
ld.acquire.sys.b32 — verify the bulk scan's does too after the recent

## Bulk RS+AG: the residual closed — two protocol bugs, not a visibility anomaly

The "mid-kernel NIC-write blindness" was a misdiagnosis, and the path to
seeing that is the interesting part. Fresh loopback runs with kernel-side
instrumentation (per-cell scan records, a claim log, exit-state cell dumps —
all failure-only prints, in-tree) replaced the CPU-side microscope as ground
truth, and the fingerprints diverged from the old story immediately:

- Run-to-run variance in WHICH segments failed (RS seg 2 one run, AG the
  next) — deterministic arithmetic bugs do not do that; races do.
- W4 kernels claimed SOME arrivals and mapped them correctly (mask bits at
  exactly the right k) while OTHERS sat unclaimed in the cells — "blindness"
  cannot be partial per-cell.
- The BKFIN `arrived=0` was ambiguous by construction: the kernel acks a
  claim BEFORE the k-guard, so "acked cell" never meant "counted arrival".

### Root cause 1: no cross-rank phase alignment + eager claiming

Doorbell rings are flight- and phase-agnostic per-(peer,lane) FIFOs, and the
shard geometry guarantees senders do NOT progress in lockstep: rank 0's shard
ends in segment 0, so its RS flight completes while rank 1 still folds RS —
rank 0 enters AG and posts AG doorbells into rank 1's still-spinning RS
kernel. The eager claim loop ate them: claimed (acked — CONSUMED), mapped
past the segment's stripe guard, rejected, and the arrival was permanently
lost to the phase that needed it. Both phases then deadlocked on each
other's starvation (the observed mutual 5s stalls, all "poison" exits).

The fix is the window discipline the j-mapping was already half of: j is the
doorbell's RING-LIFETIME arrival index and the base is self-computed at
launch, so the kernel can compute exactly which ring window belongs to this
segment — [base, base + this lane's stripe share) — and REFUSE to claim
outside it. Deferred doorbells sit in their cell for the kernel whose window
contains them; every post maps to exactly one window of the receiving flight,
in ring order, regardless of cross-rank skew. The underflow case (j < base)
falls out as a huge in_seg → skip. Kernel-only change.

### Root cause 2: "done does not imply posted", one gate further

A zero-arrival kernel (empty receive window — shard geometry makes these
routine) stamps done instantly while its OWN outbound stripes are still
being posted; the advance gate waited only for TX retirement, which is an
equality on POSTED work — unposted stripes are invisible to it. The engine
advanced, the next launch reset staged_counters to 0, and the posting loop's
release condition (staged > posted) inverted forever: measured as tx=31/31
with 5 of 16 AG stripes never posted. The advance now also requires every
peer's posted[p] == n_out before moving.

### Root cause 3: the ack certified consumption that had not happened yet

With the deadlocks cleared, the flights COMPLETED — and bitwise mismatches
appeared (mid-stripe prefix/suffix corruption, symmetric across ranks, run-
to-run-varying counts: the mid-DMA overwrite signature). The RS fold reads
payload slots through s_ptr AT KERNEL EXIT, but the ack was written AT CLAIM
time — and the ack is what returns the sender's credit, which is what frees
the ring slot. A sender a segment ahead wrapped the 8-deep ring inside one
claim-to-exit gap and DMA'd new stripes over the fold's inputs. The latency
machine never had this: single-flight serialization means the next post
cannot precede the kernel's exit. The ack now means what it always claimed
to — "payload CONSUMED" — and flushes after the fold (the AG copy consumes
at claim time but shares the mechanism). The door cell cannot move before
its credit returns, so the claimed seq is re-read at flush; no per-claim
records, just a claimed-cell bitmap.

The deferral unmasked one more hazard: a claimed cell re-presents every
scan round (its ack no longer masks it), and a re-presented cell re-enters
the shared CAS — lowest-thread-wins inside a warp — stealing the claim slot
from a fresh doorbell owned by a higher thread of the same warp, forever
(measured: arrived 1/2 with the second doorbell live in its cell for 5s).
The scan now skips the kernel's own claims via the same bitmap; the
CTA barrier between rounds publishes the bits.

## Close-out: the TSan one-off found a real lifetime bug (and it is fixed)

Re-running TSan against bus_test (first time with the collective scenarios
in the binary) surfaced 9 warnings — none of the documented libcuda class:
the waiter thread's final shared_ptr drop (BusRequest destructor:
cond_destroy/free) raced the ENGINE's trailing cv notify inside
complete_request. The flight teardowns clear the engine's references
BEFORE completing (the deliberate clear-before-wake ordering — the
single-outstanding gate), so the engine held zero references while its

stream-sync gap is milliseconds wide.

## d3 item 3 — graph capture of the decode step (§6.2)

The design: the decode step's fixed launch sequence records once and
replays per token. The collective kernel becomes a graph node; the
engine stops launching it and REACTS — per-generation cells carry the
kernel->engine handoff (ready/done/status/gen_seq), the arm step resets
cells and assigns the window's monotonic generations before each replay
(one atomic window counter; first/last derive), the engine walks
generations (single-flight: the graph serializes the kernels, so at most
one is un-done at a time), posting each gen's peer pairs from the row the
generation selects at lane-0's cursor position, advancing on done.
Session APIs: graph_record_begin / allreduce_record (on the caller's
capturing stream) / graph_record_end, then per step graph_replay_arm ->
cudaGraphLaunch -> stream sync -> graph_replay_finish. One graph era per
bus (v1): harness sends and eager collectives close at record_begin. The
per-window carrier request gives the posts request-shaped slot ownership
without a registry entry (credits recycle slots; the walk owns
completion).

Three bring-up findings, all kept for the record:

1. THE MISCOMPILE. Extracting the shared eager/graph kernel body into a
   force-inlined template (pure renames, reference-based row policies)
   broke the eager machine deterministically at -O3 — the fold read
   doorbell cells as payloads (world-4 plain, staged, and bulk-vs-
   chunked all diverged bitwise; world-2 plain alone survived). The git
   bisect was surgical: HEAD's kernel verbatim + every engine/graph
   change = green; the shared body = broken. The eager kernel is
   restored verbatim and the graph kernel is a sibling with its three
   deltas (generation read off the cell, row derivation, per-gen cell).
   A validated machine is not a refactoring test bed.

2. DONE DOES NOT IMPLY POSTED (the graph form of the bulk lesson). The
   kernel's fold waits on the PEER's doorbell, not this side's own post,
   so a fast peer can stamp done within one engine pass of ready — the
   walk advanced and discarded an unposted flight, stranding the peer's
   kernel on a doorbell that never came (measured on the first fabric
   probe: posts 131/132 with the peer's last generation spinning 5s;
   both sides symmetric). The walk now activates the flight BEFORE the
   done check and requires the posting mask complete before advancing.

3. THE UNREPRODUCED STALL (open, instrumented). One fabric run stalled
   at generation 1825 on BOTH ranks: both engines posted, both kernels
   waited, doorbells never landed, lane watchdogs fired at 5s. The
   mechanism analysis: an unconsumed doorbell freezes the ring-ordered
   recycle -> the receive queue drains over the next wrap -> the wrap's
   last sender RNR-retries forever. ~40k generations since (plus 36k
   today across two-node probes and loopback suites) have not
   reproduced it. Standing observability: a per-flight stall microscope
   (engine-side cell + lane-0 door/ack dumps, failure-only) and an
   adopt-time quiescence note (every door cell must read consumed at
   window adopt — a persisting door!=ack is the freeze precursor; the
   legal mid-flight form, the peer's next-window doorbell landing during
   the check, has been observed and looks exactly one-slot-ahead).
   The 5s bounds fail the era loudly; nothing hangs.

Gates: bus_test green x8 (4 full + 2 one-lane + 2 more post-fix) with
the new scenario_allreduce_graph (worlds 2+4: capture 3-collective steps
with GEMM stand-ins, 10 replays, every replay bitwise vs the canonical
oracle AND the eager machine's bytes; contract pins: record/arm/eager/
send rejections); ASan/UBSan clean; TSan 0 warnings x3 (coll_mode became
atomic — the graph session is a second writer); ci-local 22/22.

Fabric amortization (two nodes, TP=2, 12-collective steps,
DGPP_WARM_SPINS=2000 decode-scale stand-ins, 500 measured replays):
eager p50 33.6us per collective (submit->wait); graph step p50 357.4us

## The dense scale-grid slice bug (found by the d4 design review, fixed)

Designing the sharded loader (d4) required pinning the exact slicing
semantics GlmTpViews established — and they did not survive scrutiny.

THE BUG: `quant_rows_view` rebases the scale pointer at
floor(row_start/128) and the scale GEMM anchors its block lookup at the
LOCAL frame (scale_row = n0/128). For a slice that starts 128-aligned,
local row r's true block is row_start/128 + r/128 — exactly what the
consumer computes. For a slice that starts MID-BLOCK and CROSSES the next
boundary, local rows past the crossing need a different scale row than
the local frame serves — unrepresentable by a pointer view. Rank 1's
dense slice at world=2 (fixture inter 200: rows 100..199) read block 0's
scales for rows 128..199. The down-projection column pack had the same
shape of defect (scale column (start/128) only).

THE EVIDENCE CHAIN (each step decisive, no interpretation):
1. Kernel-vs-kernel, no CPU reference: the SAME scale GEMM on the full
   [200,256] matrix vs the rebased slice [100,200) — 265/400 outputs
   differ, worst 13.5x. The full-matrix call matches a global-index
   reference exactly (harness self-check).
2. The REAL pieces (GlmLayerStream + GlmTpViews::bind + scale GEMM) on
   the real fixture bytes: 285/400 wrong, first bad local row 28 = global
   128 = the block boundary.
3. The full FFN composition (real kernels, real fixture tensors, bind's
   exact slice/pack math, canonical fold): l2 vs the world=1 oracle =
   0.28 — 14x over the test's own 0.02 budget.
4. In-test instrumentation (env-guarded dumps of the boundary partials):
   the actual test run's layer-0 fold measures l2 0.30 vs the oracle's
   own FFN output. The bug was live in every "passing" run.

WHY THE TEST PASSED: the per-layer isolated metric compares the mHC
STREAM STATE, and the stream update's mixing coefficients ATTENUATE the
FFN boundary error ~300x (0.30 -> 0.001, comfortably under the 0.02
budget). The cross-rank BITWISE checks are correctness-orthogonal (every
rank held the same wrong fold). The free-run l2 (0.041 at world 2) was
reported, not asserted, and its drift — plus 5 "route flips" that were
the bug's noise pushing routers around — was absorbed by the near-tie
certification machinery.

WHICH PUBLISHED NUMBERS STAND: the REAL-checkpoint loopback parity
(l2 0.1522/0.1549 = the M4 tier) — the real dims (12288 dense / 2048
shared) are 128-multiples at every TP world, so the real model NEVER
produced a misaligned slice; the bug was fixture-geometry-only. The
fixture-only rows (worst layer 0.0033/0.0187, free 0.041/0.254, the
flip counts) were contaminated by the bug; the MoE-layer floors (~1e-4)
were real (shared inter 64 slices fit inside one scale block — correct
by magnitude, not by luck of the grid).

THE FIX (the contract, not a workaround):
- A rank's slice of a block-scaled matrix must start 128-aligned in the
  sliced dimension. GlmTpViews' validators reject misaligned inter
  quotients BEFORE any load; quant_rows_view and both column packs throw
  at the seam. The fixture moved to inter dims 512 (256/128-multiple
  quotients at worlds 2 and 4); the OLD geometry (200/64) is now the
  negative test — it must throw, legibly.
- The assertion surface gained the raw boundary folds: forward_isolated
  optionally captures the post-fold attention and FFN outputs per layer
  (2*num_layers vectors; world=1 receives the same buffers unfolded).
  The test asserts BOTH surfaces now — stream snapshots AND folds, the
  kept-row discipline applying to MoE FFN folds. The attenuation hole
  is closed.
- Collateral: the loader's APE conversion now reads bf16 via memcpy —
  safetensors does not align individual tensors in the file, and the
  fixture's new byte layout landed one at an odd offset (a latent
  typed-read bug, UBSan-caught).

NUMBERS (fixed fixture, same machinery): world=2 worst fold l2 0.0001
(the split-k fold rounding floor), worst layer 0.0003, free l2 0.0067,
0 route flips, 0 top-1 misses. World=4: worst fold 0.0193, worst layer
0.0200 — the same <2e-2 tier the record claimed, now earned by real
rounding rather than crossed fingers. Gates: ci-local (WERROR) 22/22,
ASan/UBSan clean, TSan 0 warnings.

The fabric fixture A/B numbers in the record above (md5-identical,
l2 0.0410) are similarly superseded — the md5 cross-rank guarantee
stands (it is correctness-orthogonal); the TP-vs-oracle l2 was the
bugged fixture's number and the re-run belongs to the d4/exit-gate
fabric validation.

## d4 — Sharded load + replicated hashes (2026-08-30, evening session)

PLAN d4: "Sharded load for TP=2 and TP=4, plus hashes for replicated
weights." Design landed as planned, with one architectural commitment
that made the whole thing verifiable: **the loader IS the slicer.**
`GlmLayerStream(cfg, dir, rank, world)` builds each resident layer
directly at the rank's local geometry (head row ranges, contiguous
whole-expert ranges, 128-aligned quant row/column slices — the §5.2
contract transfers 1:1), so only rank-local checkpoint bytes are ever
read. `GlmTpViews::bind` of a full load stays as the INDEPENDENT
reference implementation of the same slicing spec, and the new
`glm_tp_shard_parity` test pins the two BITWISE — every bound surface of
every layer (7 fixture layers incl. the MTP draft layer; KDA and DSA,
dense and MoE), both worlds. World=1 is the degenerate rank 0 of the
same build: identical grant sequence, identical bytes — the M4 path
survives by construction, and glm_loader_test's formula checks still
pass unmodified.

THE PARITY RESULT: world=2, 930 bound surfaces bitwise-equal; world=4,
1,380. The byte reconcile is the arithmetic pin:
sum_ranks(source bytes) == world1_total + (world-1) * verbatim, with the
verbatim re-read set (replicated + DSA bridge) identical across ranks —
exact at both worlds. Per-rank fixture reads: 57% at world=2, 36% at
world=4. The residue is the replicated set plus the two DSA dequant
bridges (q_b/o_proj read in full by every rank — their quant slices
would start mid-block at some worlds; they slice the dequantized bf16
instead, exactly what the views always did; documented in §5.2 until
the scale-GEMM seam retires the bridge).

BOOT HASHES: `hash_replicated()` folds every replicated tensor's raw
mmap bytes per layer (FNV-1a per tensor, summed — order-independent),
plus the globals; the loopback test asserts it rank-invariant AND equal
to the world=1 pass; the fabric runner writes it per rank
(`{out}.digest.txt`) for the offline cross-rank comparison; the model
computes it at construction (before the first forward) when world>1.

TWO BUGS THE PROCESS ITSELF CAUGHT, one of them mine:
1. The build-time read-class drift guard (verbatim load of a
   sharded-class tensor at world>1 must throw) fired on MY OWN
   classifier — the scale-strip suffix was counted 11 chars,
   "_scale_inv" is 10. The guard worked exactly as designed: the
   disagreement between the build and the classifier failed loudly in
   the first run instead of corrupting a digest.
2. The byte-reconcile failure was in MY TEST, not the product: the
   shared full stream's accumulated counters double-count when the
   parity loop reloads all layers for the second world. Per-layer
   deltas proved the loader's accounting exact (verbatim identical

THE REAL FIND (a gate run caught it): ci-local failed glm_tp_test with a
FIRST-COLLECTIVE stall — rank 1 posted, rank 0 never did, both ran to

collective; its kernel spins on rank 0's doorbell; rank 0 wakes and
calls the device-wide sync inside its layer load — which now waits for
rank 1's spinning kernel, which waits for rank 0's doorbell. Deadlock,
broken only by the 5s watchdog. This is the SAME class the M5 bring-up

seam had the identical shape and had survived months on near-zero skew.
Fabric is immune (separate devices per process); loopback-only, but
structural. Fix: load boundaries now synchronize EXACTLY the bump's
reader streams (the model's compute stream via set_reader_stream + the
