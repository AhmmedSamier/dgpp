# Qwen YaRN 512K validation on two Sparks

This record summarizes the existing 2026-09-20 validation of
[PR #3](https://github.com/HawkBearPig/dgpp/pull/3), tested at `6699b41` and
merged as `1877b13`. It was transcribed for the release notes from the
[fabric review](https://github.com/HawkBearPig/dgpp/pull/3#pullrequestreview-5259086201)
and retained release-check JSON and rank logs; it is not a new benchmark run.

## Configuration and procedure

Two DGX Spark GB10 nodes over RoCE served
`nvidia/Qwen3.8-Flash-Next-NVFP4` with the shipped
[`_w2_yarn512k` template](../../deploy/cluster_qwen-3.8-flash-next_nvfp4_w2_yarn512k.example.json):
two slots, a 532480-token BF16 KV pool, mapped n-gram table, FP8 dense
weights, decode graphs, MTP depth 1 and a 1.5-GiB prefix cache. YaRN factor
2 lifts the request ceiling from 262144 to 524288 tokens. Rank 0 journals
the scaling settings to both ranks. Omitting `engine.rope_scaling` keeps
the plain RoPE path; the [arithmetic review](https://github.com/HawkBearPig/dgpp/pull/3#pullrequestreview-5258178006)
records the unit, oracle, kernel and forward checks.

With the deployment ready on idle hardware, the release check ran once
per target length, using its default seed and five needle depths:

```bash
python3 scripts/qwen_yarn_release_check.py --run --probe-tokens 768 \
    --concurrency 2 --lengths 262144 --json-out /tmp/yarn-262144.json
python3 scripts/qwen_yarn_release_check.py --run --probe-tokens 768 \
    --concurrency 2 --lengths 524288 --json-out /tmp/yarn-524288.json
```

The probe budget covers the checkpoint's reasoning before its answer.
Target length is approximate; the table reports actual rendered prompt
tokens. The [runbook](../../docs/qwen_yarn_release_check.md) describes
deployment preparation and the check's phases.

## Results

| Measurement | 262144 target | 524288 target |
| --- | ---: | ---: |
| Rendered prompt tokens | 261388 | 522619 |
| Retrieval at depths 5%, 25%, 50%, 75%, 95% | 5/5 | 5/5 |
| Cold prefill | 237.5 s | 730.1 s |
| Cold prefill per computed token | 0.909 ms | 1.397 ms |
| Two submitted streams completed | 2/2, no errors | 2/2, no errors |
| Wall time for those two streams | 243 s | 1475 s |
| Short-context control (4096 target) | 5/5 | 5/5 |
| Peak process GPU memory, rank 0 | 51787 MiB | 51787 MiB |

All retrieval probes finished with `stop`; both release checks reported
PASS. The fabric review records no ERROR lines on either rank and matching
operation streams at teardown. The long-context decode follow-up
[#19](https://github.com/HawkBearPig/dgpp/issues/19) reports approximately
60.7 / 96.0 ms per pass at 261K / 522K, with MTP yield around 1.9 tokens
per pass. These are engine-pass timings at long context, separate from
the script's short-context `decode` phase.

## Measurement limits

This is a five-needle retrieval check at one seed on the NVFP4 two-node
recipe. The two-stream result measures completion including queueing;
the 512K pool does not seat two full-length requests at once. The script's
`ms_per_token` fields have an extra factor of 1000, and its cache-reuse
probe repeated an entry after eviction, reporting zero reuse. Neither
field establishes a performance or cache regression; corrections are
tracked in [#16](https://github.com/HawkBearPig/dgpp/issues/16).
Shared-document reuse with different question tails is separately tracked
in [#17](https://github.com/HawkBearPig/dgpp/issues/17).
