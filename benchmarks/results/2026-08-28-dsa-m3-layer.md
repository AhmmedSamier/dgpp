|---|---|---|

Measured bottlenecks before each fix (clock64 phase timers, since removed):
the select merge's single-block bitonic was 97% of the select kernel; the
warp-strided merge key loads serialized 512 dependent global loads per warp
(57%); attention's unpadded [head][512]/[group][64] smem layout bank-
conflicted every access 32 ways (85% of attention cycles).

## Interpretation

- The projection GEMMs (cuBLASLt, m=1) now dominate decode at ~1.0 ms —
  238 MiB of weights at ~240 GB/s, i.e. AT the planning floor. Custom
  kernels account for the remaining ~1.2 ms (select 0.55, attention 0.2,
  absorb+vout 0.2, norms/updates 0.1); the select merge's single-block
  bitonic (0.2 ms) is the largest remaining custom-kernel cost and the next
  optimization target if decode must approach the roofline.
- Graph replay matches eager within noise (no launch-bound behavior).
- Prefill throughput drops at 8,192-token chunks: the dot-tile budget
  (64 MiB) shrinks query tiles to ~30 rows at that context, multiplying
  K-cache gather+GEMM passes. A larger dot budget or persistent per-request
  gather buffer would recover it if prefill is the binding constraint.
- Run-to-run repeat (5-iter vs 30-iter runs) agrees within 1.5%.

### Bugs found by this first execution of the torch backend

Never-executed code is untested code; the path had four defects:

1. FP8 block dequantization divided by `weight_scale_inv` instead of
   multiplying (empirically grounded: multiply gives std 0.015 on
   q_a_proj, divide 5.6e5). The scale name also missed the checkpoint's
   actual suffix.
2. Indexer weight names did not match the checkpoint (`indexer.gate` vs
   `index_kpool_compress_gate`, etc.).
3. The absorbed-attention fold used `q @ w_uk.T` instead of `q @ w_uk`.
4. The selection logits paired DECODED q_fp8 with RAW uint8 index_k bytes
   (`.float()` on the code tensor). This one is insidious: e4m3 values are
   monotone in the raw byte within each sign class, so rankings stay
   near-correct and the failure is a single boundary swap — the structural
   tolerance absorbed it as "1 flip, OK" while the ENGINE was right and
   the reference was wrong.

Hardening in response: the dump-parity runner now certifies every flipped
row with the full near-tie audit (`tests/cuda/dsa_near_tie_audit.hpp`) —
device row re-derived bitwise from the device's own q_fp8/w_folded/dots,
reference re-derived from the dump's own weights and cache — instead of
tolerating flips by budget. Verified in both directions: clean corpus
passes with 0 flips; a corrupted reference row (mid-rank pool swapped into
the sparse row, mimicking bug 4's signature) is rejected with
"NOT a boundary near tie" and exit 1. The run is shaped single-tile (dot
budget sized for all rows) so every row's tensor-core dots are available
to the audit.

The q-path power-of-two scale also switched from a `torch.log2` form to the
shared exact-bit helper, and torch's e4m3 cast was cross-checked bit-exact
against the hand codec over a 1.1M-value sweep (subnormals, boundaries).
