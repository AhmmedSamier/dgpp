## API check

`usage cached_tokens` failed: the prefix cache snapshot alignment is the 128-token block, so a
prompt shorter than a block never reaches a cut and is not cached (a prompt past 128 tokens caches
— the class and concurrency runs show entries accumulating). Lowering the alignment to cache short
prompts is a scoped follow-up: the sub-block partial-block copy lands on the CSA2 state pool, a
second paged pool the scheduler's block reservation does not size, and it crashed the four-slot
world under load. Reverted to the block alignment (plan §8).

The mechanism in the numbers: the pass got cheaper (chat 71 → 46 ms) while the
tokens it commits barely moved (2.23 → 1.99) — fewer rows, the same accepted
prefix. The per-position acceptance the engine now reports is conditional on
the position being verified: at λ 0.045 it reads p1 77 % p2 74 % p3 75 % p4 85 %
p5 87 % (rank 0's stats), i.e. the positions the policy lets through stand —
the confidence head is calibrated. The higher λ (the achieved throughput,
the Dinkelbach fixed point, rather than the plain step's reservation rate) is
2–4 % better on every class; the deploy example now carries it. Costs: the
scheduled path loses the pipelined launch-ahead (~0.5 ms/step) — invisible
here, every class gained — and 4 reduced-depth variants per slot (7–21 MiB
each; warm capture 0.63 → 0.76 s). Not scheduled: the batched replay (two live
requests verify the full block) and sampled requests.
